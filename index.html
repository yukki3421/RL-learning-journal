VLA-RL Placement Lab

做一个“机械臂把物体放到盘子里”的单任务 RL 实验仓库。沿用现有 README 的 RL4VLA + PPO 主线，复用作者的 warm-up 检查点；自己的工作落在训练与评估封装、实验追踪、前后对比、失败分析和一个位置泛化实验上。

终点：可运行的代码 + 可追溯的结果 + 可观看的 Demo

锁定最小可交付范围

  • 任务：优先核验 RL4VLA 中 PutOnPlateInScene25Single-v1 与 warm-up 检查点的训练适配；Day 10 冻结实际任务 ID、配置和成功条件。
  • 方法：初始 VLA → 单任务 PPO 微调；第一轮不加入 GRPO、SAC、多任务或真机。
  • 比较：同一初始策略与自己训练的策略，使用相同的独立评估集合。作者 RL 检查点只能作为参考。
  • 实验：只改变物体初始位置。明确训练范围、测试范围以及二者是否重叠。
  • 个人贡献：可重复运行的入口、评估协议、逐 episode 数据、失败归因与实验报告；保留上游引用。
交付不依赖“必须涨分”。必须走通训练→保存→独立加载→评估。预设希望成功率提高 ≥10 个百分点，但这只是探索目标；未提升时，用完整日志和失败分析说明结果，不选择性报告。

三个阶段闸门，保证项目落地

  1. Day 7 · 资源可行。拿到实际 GPU / 驱动信息，能启动仿真、渲染、加载模型并完成一次推理。当前会话无法读取 GPU，不能据此断定机器无 GPU。
  2. Day 14 · 路线冻结。主线仍不可运行时，切换到 ManiSkill PickCube-v1 的小策略 PPO，沿用后续训练、评估、泛化与交付里程碑。在日志中逐项替换 VLA 专属任务，明确“VLA 微调尚未完成”，不把小策略实验称作 VLA 结果。
  3. Day 28 · 工程闭环。必须有自己更新得到的检查点、独立评估 CSV 和视频。没有闭环则暂停新实验，先修复；压缩额外种子与非核心文档，保留发布周。
资源预算：默认每天 2–3 小时主动投入，每周一天缓冲；GPU 训练时长另算。RL4VLA 上游示例区分单张 80GB 与两张 40GB 的布局，这不是最低配置承诺。先测峰值显存和每轮耗时，再确定并行度、训练步数与种子预算。

本地保存与备份

这是不依赖后端的单文件网页。进度存在当前浏览器的 localStorage，不会写回 HTML，也不会自动同步到其他设备或 GitHub。

浏览器、访问地址、端口或文件位置变化后，可能看不到原记录。切换前先“导出进度”，再在新位置导入。隐私模式、清理浏览器数据或存储被禁用会影响保存；页面会提示保存失败。

可双击 index.html 打开；在远程开发环境中，可运行 python -m http.server 8000 --bind 127.0.0.1，通过 SSH / 编辑器转发 8000 端口后访问。网页可离线使用；外部文档链接需要网络。
